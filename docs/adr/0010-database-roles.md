# 0010 — Database roles, migrations and test databases

## Context

The app stores minors' names and statements. A bug or an injected query in
the web process must not be able to change the schema, switch off a trigger
or rewrite the audit log. Migrations have to be reviewable, and the
integration tests should prove the privileges, not bypass them.

## Decision

- **Migrations** are SQL in `drizzle/`, generated by drizzle-kit from the
  schema in `src/infra/db/schema/` (`pnpm db:generate`). Triggers, functions
  and grants go into custom migrations (`pnpm db:generate --custom`). The
  one-shot `migrate` service applies them (`pnpm cli migrate`) as the schema
  owner, under an advisory lock. The web and worker processes never migrate.
- **Roles.**

  | Role | Login | Privileges |
  |---|---|---|
  | owner (migrator) | yes | owns the schema; used only by `migrate` |
  | `autoporada_app` | no (group) | DML on every table in `public` |
  | `autoporada_backup` | no (group) | `SELECT` on `public` and the migration history |

  The operator creates the login roles for `web`, `worker` and `backup` and
  makes them members of the group roles, with passwords from Docker secrets.
  Migration `0000_roles` creates the group roles if they do not exist yet.
- **Default privileges** grant every new table to the group roles once, in
  `0000_roles`. A table that needs less (the append-only audit log) revokes
  in its own migration.
- Rules that must also bind the owner (append-only audit, at least one
  active headmaster) are **triggers**, not just missing grants. Every
  trigger function pins `search_path = pg_catalog, public, pg_temp` and
  qualifies its tables, and PUBLIC has no `TEMPORARY` privilege: a
  temporary table must never stand in for a real one. The migrator owns the
  database, so that revoke takes effect.
- **Tests.** Each integration test file gets its own database, cloned from a
  template that is rebuilt only when `drizzle/` changes. The app connection
  in tests runs as `autoporada_app`, so every test also exercises the grants.

## Consequences

- A missing grant or an over-broad one fails in the tests, not in production.
- Adding a table needs no grant; restricting one is explicit and reviewed.
- The RUNBOOK (M11) documents creating the login roles.
